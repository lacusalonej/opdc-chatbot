# เอกสารระบบหลังบ้านแอดมิน — OPDC Chatbot (ก.พ.ร.)

เอกสารนี้อธิบายการติดตั้ง, การจัดการ, การสำรองข้อมูล, การใช้งาน API และข้อจำกัดของระบบหลังบ้านแอดมิน (Admin Dashboard) เขียนเป็นภาษาไทยทั้งหมด

---

## 1. ภาพรวมระบบ

ระบบหลังบ้านแอดมินสร้างขึ้นบน Express.js รันที่พอร์ต 8001 ใช้ฐานข้อมูล SQLite สำหรับข้อมูลแอดมิน (ผู้ใช้, เซสชัน, บันทึกการดำเนินการ, คอนฟิกระบบ, ประวัติการสนทนา) และใช้ไฟล์ JSON สำหรับฐานความรู้ (knowledge chunks)

คุณสมบัติหลัก:
- ล็อกอิน / ออกจากระบบแบบรักษาเซสชัน (session-based auth)
- รหัสผ่านแฮชด้วย bcrypt (SALT_ROUNDS = 12)
- จำกัดจำนวนครั้งล็อกอิน (rate limiting) 10 ครั้งต่อ IP ภายใน 15 นาที
- ป้องกัน CSRF แบบ double-submit token (ส่งผ่าน header `X-CSRF-Token`)
- ควบคุมสิทธิ์ตามบทบาท (RBAC): admin / editor / viewer
- ตาม PDPA: ลบประวัติการสนทนาได้, เซสชันแชทเก็บเฉพาะใน RAM
- บันทึกบันทึกการดำเนินการ (audit log) ทุกการเปลี่ยนแปลงสำคัญ

ต้นกำหนด API: `/api/admin/v1/*`

## 3. การติดตั้งและรันเซิร์ฟเวอร์

### 3.1 ติดตั้ง dependencies

```bash
cd backend
npm install
```

### 3.2 ตั้งค่าตัวแปรสภาพแวดล้อม

สร้างไฟล์ `.env` ในโฟลเดอร์ `backend/` (หรือส่งผ่านตัวแปรสภาพแวดล้อมก่อนรัน):

```env
PORT=8001
NODE_ENV=development
ADMIN_SESSION_SECRET=<สตริงสุ่มอย่างน้อย 32 ตัวอักษร เช่น เปลี่ยนทุกครั้งที่ติดตั้งใหม่>
```

หมายเหตุ: ใน production ต้องตั้ง `ADMIN_SESSION_SECRET` เสมอ มิฉะนั้นเซิร์ฟเวอร์จะไม่เริ่มทำงาน (ระบบจะหยุดด้วยข้อผิดพลาดร้ายแรง)

### 3.3 รันเซิร์ฟเวอร์

```bash
# โหมดปกติ
npm start

# โหมดพัฒนา (รันอัตโนมัติเมื่อไฟล์เปลี่ยน)
npm run dev
```

เซิร์ฟเวอร์จะรันที่ `http://localhost:8001` และตรวจสอบสถานะได้ที่ `http://localhost:8001/health`

## 4. การสร้างบัญชีแอดมินคนแรก (First Admin Provisioning)

ก่อนใช้งานระบบหลังบ้าน ต้องสร้างบัญชีแอดมินคนแรกผ่านสคริปต์ provisioning:

```bash
cd backend
ADMIN_USERNAME=admin ADMIN_PASSWORD=ChangeMe123! ADMIN_ROLE=admin node scripts/create-admin.js
```

ข้อกำหนดรหัสผ่าน: อย่างน้อย 8 ตัวอักษร

หลังสร้างแล้ว รหัสผ่านจะถูกแฮชด้วย bcrypt ก่อนบันทึกลงฐานข้อมูล ไม่มีการเก็บรหัสผ่านเป็นข้อความธรรมดา

หากบัญชีนี้มีอยู่แล้ว สคริปต์จะแจ้งว่า `"ผู้ใช้ 'admin' มีอยู่แล้วในระบบ"`

## 5. การตรวจสอบสิทธิ์และเซสชัน

### 5.1 ล็อกอิน

```
POST /api/admin/v1/auth/login
Content-Type: application/json

{
  "username": "admin",
  "password": "ChangeMe123!"
}
```

ตอบกลับ (สำเร็จ):
```json
{
  "status": "success",
  "message": "ล็อกอินสำเร็จ",
  "user": { "id": 1, "username": "admin", "role": "admin" },
  "csrfToken": "..."
}
```

เซิร์ฟเวอร์จะตั้งคุกกี้ `session_id` (httpOnly, sameSite=lax) และสร้าง CSRF token เก็บในเซสชัน

### 5.2 ดึง CSRF token (สำหรับคำขอครั้งถัดไป)

```
GET /api/admin/v1/auth/csrf-token
Cookie: session_id=...
```

ต้องล็อกอินก่อนจึงจะดึง token ได้

### 5.3 ดูข้อมูลผู้ใช้ที่ล็อกอินอยู่

```
GET /api/admin/v1/auth/me
Cookie: session_id=...
```

### 5.4 ออกจากระบบ

```
POST /api/admin/v1/auth/logout
Cookie: session_id=...
X-CSRF-Token: <csrfToken ที่ได้จากล็อกอินหรือ /csrf-token>
```

ตอบกลับ (สำเร็จ): `{ "status": "success", "message": "ออกจากระบบแล้ว" }`

หลังออกจากระบบ เซสชันจะถูกทำลายบนเซิร์ฟเวอร์ และคุกกี้ `session_id` จะถูกล้าง

### 5.5 บทบาทและสิทธิ์ (RBAC)

| บทบาท | สามารถดูได้ | สามารถแก้ไขได้ | สามารถลบได้ |
|-------|-----------|-------------|---------|
| admin | ทุกหน้า | ทุกหน้า | ทุกหน้า |
| editor | ทุกหน้า | knowledge, prompt | knowledge |
| viewer | ทุกหน้า (อ่านอย่างเดียว) | ไม่ได้ | ไม่ได้ |

### 5.6 การจำกัดอัตราการล็อกอิน (Rate Limiting)

เพื่อป้องกันการโจมตีแบบเดารหัสผ่าน (brute force attack) ระบบจะจำกัดจำนวนครั้งที่พยายามล็อกอินล้มเหลวต่อหนึ่ง IP ดังนี้:

| รายละเอียด | ค่า |
|-----------|-----|
| จำนวนครั้งสูงสุดที่ล็อกอินผิดได้ | 10 ครั้ง |
| ระยะเวลาที่นับ | ภายใน 15 นาที |
| ผลเมื่อเกินขีดจำกัด | IP จะถูกบล็อกชั่วคราว 15 นาที (ตอบสถานะ 429) |

#### สิ่งที่ผู้ใช้ต้องทราบ
- **ล็อกอินสำเร็จ** → IP จะไม่ถูกบล็อก ใช้งานได้ตามปกติ
- **ล็อกอินผิด 1–9 ครั้ง** → แต่ละครั้งจะได้รับสถานะ 401 (ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง) IP ยังไม่ถูกบล็อก
- **ล็อกอินผิดครบ 10 ครั้งภายใน 15 นาที** → IP จะถูกบล็อกชั่วคราว จะได้รับสถานะ 429 (Too Many Requests)
- **หลังจากถูกบล็อก** → ต้องรอ 15 นาทีนับจากครั้งล่าสุดที่ถูกบล็อก แล้วจึงลองล็อกอินอีกครั้ง
- **การบล็อกไม่ถาวร** – หลังจาก 15 นาทีผ่านไป IP จะกลับมาใช้งานได้ตามปกติ

> หมายเหตุ: การจำกัดอัตรานี้มีผลเฉพาะ IP ที่พยายามล็อกอินผิดเท่านั้น ผู้ใช้ที่ล็อกอินถูกรหัสจะไม่ได้รับผลกระทบ หากผู้ใช้หลายคนแชร์ IP เดียวกัน (เช่น ออกจากเครื่องเดียวกันผ่าน NAT) จะถูกนับรวมกันเป็น IP เดียว

## 6. CSRF Protection (ป้องกันการปลอมแปลงคำขอ)

ทุก endpoint ที่เปลี่ยนสถานะ (POST, PUT, DELETE) ต้องส่ง header `X-CSRF-Token` ที่ตรงกับค่าในเซสชัน หากไม่ส่งหรือส่งไม่ตรง จะตอบกลับ `403 CSRF token ไม่ถูกต้อง`

Endpoint ที่มี CSRF ป้องกัน:
- `POST /api/admin/v1/auth/logout`
- `POST /api/admin/v1/knowledge/chunks`
- `DELETE /api/admin/v1/knowledge/chunks/:id`
- `PUT /api/admin/v1/prompt/config`
- `PUT /api/admin/v1/system/config/:key`
- `DELETE /api/admin/v1/conversations/:id`

การหมุน CSRF token: dashboard หน้าเว็บจะดึง token ใหม่จาก `GET /csrf-token` หลังทุกคำขอที่เปลี่ยนสถานะสำเร็จ

## 7. API Reference (สรุปจุดสิ้นสุด API)

## 8. การสำรองและกู้คืนข้อมูล (Backup & Restore)

### 8.1 สำรองฐานข้อมูล SQLite

ฐานข้อมูลอยู่ที่ `backend/database/admin.db` สำรองโดยการคัดลอกไฟล์:

```bash
# สร้างสำเนาสำรองพร้อมวันที่
cp backend/database/admin.db backend/database/admin.db.backup.$(date +%Y%m%d%H%M%S)
```

### 8.2 สำรองฐานความรู้ (JSON)

ฐานความรู้เก็บเป็นไฟล์ JSON ในโฟลเดอร์ที่ `knowledgeManager` ใช้ (โดยปกติอยู่ภายใต้ `backend/data/` หรือตรงที่ระบุในโค้ด) สำรองโดยการคัดลอกไฟล์ JSON ทั้งหมดในโฟลดร์นั้น

### 8.3 กู้คืน

หยุดเซิร์ฟเวอร์ แล้วคัดลอกไฟล์สำรองกลับทับ `admin.db` (และไฟล์ JSON ของฐานความหากมีการเปลี่ยนแปลง) แล้วเริ่มเซิร์ฟเวอร์ใหม่

## 9. PDPA และความปลอดภัย

- **เซสชันแชทเก็บใน RAM เท่านั้น** — เมื่อเซิร์ฟเวอร์รีสตาร์ทหรือเซสชันหมดอายุ ข้อมูลแชทจะสูญหาย (ไม่ถูกบันทึกถาวร)
- **ลบประวัติการสนทนาได้** ตามคำขอของเจ้าของข้อมูล (สิทธิ์ลบข้อมูล / Right to erasure) ผ่าน `DELETE /api/admin/v1/conversations/:id`
- **รหัสผ่านแฮชด้วย bcrypt** (12 salt rounds) ไม่เก็บเป็นข้อความธรรมดา
- **คุกกี้เซสชัน** ตั้งค่า httpOnly, sameSite=lax, secure (เฉพาะ production)
- **อัตรา limitada การล็อกอิน** ป้องกันการเดารหัสผ่าน (brute force) สูงสุด 10 ครั้งต่อ IP ภายใน 15 นาที
- **ไม่เปิดเผยว่ามีผู้ใช้หรือไม่** — การล็อกอินล้มเหลวไม่ว่าจะเพราะชื่อผู้ใช้ไม่มีหรือรหัสผิด จะตอบกลับข้อความเดียวกัน `"ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง"` (สถานะ 401)

---

## 10. ข้อจำกัดของระบบ (Limitations)

1. **ฐานความรู้เก็บเป็นไฟล์ JSON** ไม่ใช่ฐานข้อมูล-relational เหมาะกับข้อมูลปานกลาง หากข้อมูลมากอาจต้องย้ายไปใช้ฐานข้อมูลที่เหมาะสมกว่า
2. **เซสชันแชทอยู่ใน RAM** — สูญหายเมื่อเซิร์ฟเวอร์รีสตาร์ท
3. **CSRF token ไม่ถูกหมุนหลังทุกคำขอที่เปลี่ยนสถานะ** แม้เอกสารจะระบุไว้ (dashboard หน้าเว็บจัดการการดึง token ใหม่ด้วยตนเอง)
4. **Rate limit ตาม IP** — หากผู้ใช้หลายคนแชร์ IP เดียวกัน (เช่น ออกจากเครื่องเดียวกันผ่าน NAT) จะถูกนับรวมกัน
5. **ไม่มีระบบลืมรหัสผ่าน / รีเซ็ตรหัสผ่าน** ในเวอร์ชันนี้ ต้องสร้างบัญชีใหม่หรือแก้ไขผ่านฐานข้อมูลโดยตรง

## 11. ขั้นตอนทดสอบด้วยมือ (Manual Test Procedures)

เนื่องจากสภาพแวดล้อมนี้จำกัดการรันสคริปต์ผ่าน Bash คุณสามารถทดสอบด้วย `curl` ได้ดังนี้ (รันจากโฟลเดอร์ `backend`):

### 11.1 ทดสอบล็อกอินรหัสผิด (คาดหวัง 401)

```bash
curl -s -o /dev/null -w "%{http_code}" -X POST http://localhost:8001/api/admin/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"nonexistent_user","password":"wrongpassword"}'
```
ผลลัพธ์ที่คาดหวัง: `401`

### 11.2 ทดสอบการจำกัดอัตรา (rate limiting) → คาดหวัง 429

**คำเตือน:** ขั้นตอนนี้จะบล็อก IP ของคุณชั่วคราว 15 นาที หลังจากครบ 10 ครั้ง ให้ทำเป็นข้อสุดท้าย

```bash
for i in $(seq 1 11); do
  code=$(curl -s -o /dev/null -w "%{http_code}" -X POST http://localhost:8001/api/admin/v1/auth/login \
    -H "Content-Type: application/json" \
    -d '{"username":"nonexistent_user","password":"wrongpassword"}')
  echo "ครั้งที่ $i: HTTP $code"
done
```
ผลลัพธ์ที่คาดหวัง: ครั้งที่ 11 (หรือก่อนหน้านั้นหากมีคำขอล็อกอินอื่นก่อน) ควรได้ `429`

### 11.3 ทดสอบล็อกอินสำเร็จ → ออกจากระบบ → ตรวจสอบเซสชัน

ต้องมีบัญชีแอดมินอยู่ในระบบก่อน (สร้างผ่าน create-admin.js):

```bash
# 1) ล็อกอิน (บันทึกคุกกี้และ csrfToken)
curl -c cookies.txt -s -X POST http://localhost:8001/api/admin/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"ChangeMe123!"}'

# 2) ดึง CSRF token
curl -b cookies.txt -s http://localhost:8001/api/admin/v1/auth/csrf-token

# 3) ดูข้อมูลผู้ใช้ (ต้องได้ 200)
curl -b cookies.txt -s http://localhost:8001/api/admin/v1/auth/me

# 4) ออกจากระบบ (ส่ง csrfToken ด้วย)
curl -b cookies.txt -c cookies.txt -s -X POST http://localhost:8001/api/admin/v1/auth/logout \
  -H "X-CSRF-Token: <csrfToken>"

# 5) ตรวจสอบหลังออกจากระบบ (ต้องได้ 401)
curl -b cookies.txt -s http://localhost:8001/api/admin/v1/auth/me
```

ผลลัพธ์ที่คาดหวัง: ขั้นตอน 3 ได้ `200`, ขั้นตอน 4 ได้ `200`, ขั้นตอน 5 ได้ `401`

## 14. คู่มือการใช้หน้าเว็บแอดมิน (Admin Pages User Guide)

หน้าเว็บแอดมินทั้งหมดอยู่ในโฟลเดอร์ `admin/pages/` เป็นไฟล์ HTML/JS แบบ static ใช้ API Client ร่วมจาก `admin/assets/js/app.js` ซึ่งจัดการตรวจสอบสิทธิ์, หมุน CSRF token, และส่งคุกกี้เซสชัน (`session_id`) ไปกับทุกคำขอ

ก่อนใช้งานหน้าใด ๆ ต้องล็อกอินผ่านหน้า `login.html` ก่อน หากยังไม่ได้ล็อกอิน หรือเซสชันหมดอายุ ระบบจะนำกลับไปหน้าเข้าสู่ระบบโดยอัตโนมัติ

---

### 14.1 หน้าเข้าสู่ระบบ (`login.html`)

**เส้นทาง:** `admin/pages/login.html`  
**บทบาท:** — (ยังไม่ต้องล็อกอิน)  
**API ที่ใช้:** `POST /api/admin/v1/auth/login`

หน้าสำหรับล็อกอินเข้าสู่ระบบหลังบ้านแอดมิน

**ฟีเจอร์หลัก:**
- ฟอร์มกรอกชื่อผู้ใช้และรหัสผ่าน
- เมื่อล็อกอินสำเร็จ ระบบจะเก็บเซสชันและ CSRF token แล้วนำไปยังหน้าแดชบอร์ด (`dashboard.html`)
- แสดงข้อความสถานะ (สำเร็จ/ผิดพลาด) ภาษาไทย

**ขั้นตอนการใช้งาน:**
1. เปิดหน้า `login.html` ในเบราว์เซอร์
2. กรอกชื่อผู้ใช้และรหัสผ่านที่สร้างไว้ผ่าน `scripts/create-admin.js`
3. คลิกปุ่ม "เข้าสู่ระบบ"
4. หากสำเร็จ จะถูกนำไปยัง `dashboard.html` โดยอัตโนมัติ
5. หากผิดพลาด จะแสดงข้อความแจ้ง error ที่ด้านบนฟอร์ม

**หมายเหตุ:** คุกกี้ `session_id` ตั้งค่าเป็น httpOnly จึงไม่สามารถอ่านผ่าน JavaScript ได้ ป้องกันการโจมตีแบบ XSS

---

### 14.2 หน้าแดชบอร์ด (`dashboard.html`)

**เส้นทาง:** `admin/pages/dashboard.html`  
**บทบาท:** admin / editor / viewer (ทุกบทบาท)  
**API ที่ใช้:** `GET /api/admin/v1/dashboard/stats`, `GET /api/admin/v1/auth/me`

หน้าภาพรวมสถิติและสถานะของระบบ แสดงตัวเลขสำคัญและข้อมูลบัญชีผู้ใช้ที่ล็อกอินอยู่

**ฟีเจอร์หลัก:**
- แถบสถิติ: จำนวนผู้ดูแลระบบ, ประวัติการสนทนา, บันทึกการดำเนินการ
- การเข้าถึงตามบทบาท (RBAC): อธิบายสิทธิ์ของ admin, editor, viewer
- แสดงชื่อผู้ใช้และบทบาทปัจจุบัน
- ปุ่มออกจากระบบ (Logout)

**ขั้นตอนการใช้งาน:**
1. หลังล็อกอิน ระบบจะนำมายังหน้านี้โดยอัตโนมัติ
2. ดูสถิติภาพรวมในการ์ดสถิติด้านบน
3. ดูข้อมูลบัญชีผู้ใช้ในการ์ด "ข้อมูลบัญชีผู้ใช้"
4. ศึกษาสิทธิ์ตามบทบาทในการ์ด "การเข้าถึงตามบทบาท"
5. คลิก "ออกจากระบบ" เพื่อออกจากระบบเมื่อใช้งานเสร็จ

---

### 14.3 หน้าจัดการความรู้ (`knowledge.html`)

**เส้นทาง:** `admin/pages/knowledge.html`  
**บทบาท:** admin / editor (ดูได้ทุกบทบาท, แก้ไขได้เฉพาะ admin และ editor)  
**API ที่ใช้:** `GET /api/admin/v1/knowledge/chunks`, `POST /api/admin/v1/knowledge/chunks`, `DELETE /api/admin/v1/knowledge/chunks/:id`

หน้าสำหรับจัดการฐานความรู้ (knowledge chunks) ที่ใช้ตอบคำถามใน Chatbot

**ฟีเจอร์หลัก:**
- ฟอร์มเพิ่มชิ้นข้อมูลใหม่ (ชื่อ/ที่มา + เนื้อหาข้อความ)
- รายการชิ้นข้อมูลทั้งหมด แสดงในตาราง (รหัส, ชื่อ/ที่มา, ประเภทสถานะ, วันที่อัพโหลด, การดำเนินการ)
- ปุ่มลบชิ้นข้อมูลแต่ละรายการ (มีการถามยืนยันก่อนลบ)
- แสดงจำนวนชิ้นข้อมูลทั้งหมด

**ขั้นตอนการใช้งาน:**
1. เพิ่มชิ้นข้อมูล: กรอกชื่อหรือที่มา (เช่น นโยบายการลาป่วย.pdf) และเนื้อหาข้อความ แล้วคลิก "เพิ่มชิ้นข้อมูล"
2. ระบบจะแยกข้อความเป็นชิ้นย่อยโดยอัตโนมัติเพื่อให้ค้นหาได้ง่ายขึ้น
3. ดูรายการชิ้นข้อมูลทั้งหมดในตารางด้านล่าง
4. ลบชิ้นข้อมูล: คลิกปุ่ม "ลบ" แล้วยืนยันการลบในกล่องโต้ตอบ

**หมายเหตุ:** ชิ้นข้อมูลที่เพิ่มจะถูกใช้โดย Chatbot ทันทีสำหรับการค้นหาคำตอบ ตามฐานความรู้ใน `knowledge/opdc-knowledge.json` และไฟล์ที่อัพโหลดเพิ่มเติม

### 14.4 หน้าจัดการ Intent (`intents.html`)

**เส้นทาง:** `admin/pages/intents.html`  
**บทบาท:** admin / editor / viewer (อ่านอย่างเดียว)  
**API ที่ใช้:** `GET /api/admin/v1/intents`

หน้าสำหรับดูรายการหมวดหมู่ Intent ทั้งหมดที่ Chatbot สามารถจำแนกได้ (14 หมวดหมู่) อิงการจับคู่คีย์เวิร์ด

**ฟีเจอร์หลัก:**
- รายการ Intent ทั้งหมด แสดงในตาราง (รหัส Intent, คำอธิบายภาษาไทย)
- แสดงจำนวน Intent ทั้งหมด

**ขั้นตอนการใช้งาน:**
1. เปิดหน้า `intents.html` ระบบจะโหลดรายการ Intent มาแสดงโดยอัตโนมัติ
2. ดูรหัส Intent และคำอธิบายภาษาไทยของแต่ละหมวดหมู่
3. ใช้รหัส Intent นี้อ้างอิงเมื่อต้องการทราบว่าคำถามใดอยู่ในหมวดหมู่ใด

**หมายเหตุ:** รายการ Intent ถูกกำหนดไว้ในโค้ด (`intentClassifier.js`) ไม่สามารถเพิ่ม/แก้ไข/ลบผ่านหน้าเว็บนี้ได้ หากต้องการเปลี่ยนแปลงต้องแก้ไขโค้ดและรีสตาร์ทเซิร์ฟเวอร์

### 14.5 หน้าตั้งค่า Prompt (`prompts.html`)

**เส้นทาง:** `admin/pages/prompts.html`  
**บทบาท:** admin / editor / viewer (ดูได้ทุกบทบาท, แก้ไขได้เฉพาะ admin)  
**API ที่ใช้:** `GET /api/admin/v1/prompt/config`, `PUT /api/admin/v1/prompt/config`

หน้าสำหรับดูและอัปเดตเวอร์ชันของเทมเพลต Prompt ที่ใช้สร้างคำตอบของ Chatbot

**ฟีเจอร์หลัก:**
- ดูเวอร์ชัน Prompt ปัจจุบัน (Key, Value, คำอธิบาย, อัปเดตเมื่อ)
- ฟอร์มอัปเดตเวอร์ชันใหม่และคำอธิบาย
- ปุ่ม "แก้ไข" / "ยกเลิก" เพื่อสลับโหมดแก้ไข
- เฉพาะบทบาท admin เท่านั้นที่แก้ไขได้

**ขั้นตอนการใช้งาน:**
1. เปิดหน้า `prompts.html` ระบบจะแสดงเวอร์ชัน Prompt ปัจจุบัน
2. คลิก "แก้ไข" เพื่อเปิดฟอร์มอัปเดต
3. กรอกเวอร์ชันใหม่ (เช่น 1.0.1) และคำอธิบายการเปลี่ยนแปลง
4. คลิก "อัปเดตเวอร์ชัน" เพื่อบันทึก
5. คลิก "ยกเลิก" หากไม่ต้องการแก้ไข

### 14.6 หน้าประวัติการสนทนา (`conversations.html`)

**เส้นทาง:** `admin/pages/conversations.html`  
**บทบาท:** admin / editor / viewer (ดูได้ทุกบทบาท, ลบได้เฉพาะ admin)  
**API ที่ใช้:** `GET /api/admin/v1/conversations`, `DELETE /api/admin/v1/conversations/:id`

หน้าสำหรับดูและจัดการประวัติการสนทนาระหว่างผู้ใช้กับ Chatbot ตามนโยบาย PDPA (สิทธิ์ลบข้อมูล)

**ฟีเจอร์หลัก:**
- รายการประวัติการสนทนา แสดงในตาราง (เวลา, Session ID, ข้อความผู้ใช้ (ตัดบางส่วน), Intent, การดำเนินการ)
- ปุ่มลบประวัติการสนทนาแต่ละรายการ (มีการถามยืนยันก่อนลบ ตามนโยบาย PDPA)
- แสดงจำนวนประวัติทั้งหมด

**ขั้นตอนการใช้งาน:**
1. เปิดหน้า `conversations.html` ระบบจะโหลดประวัติการสนทนามาแสดง
2. ดูรายการประวัติในตาราง แต่ละแถวแสดง เวลา, Session ID, ข้อความผู้ใช้, Intent
3. ลบประวัติ: คลิกปุ่ม "ลบ" แล้วยืนยันการลบในกล่องโต้ตอบ (ตามนโยบาย PDPA)
4. ประวัติที่ลบแล้วจะไม่สามารถกู้คืนได้

**หมายเหตุ:** ตามนโยบาย PDPA เซสชันแชทเก็บเฉพาะใน RAM เท่านั้น ไม่ถูกบันทึกถาวร เมื่อเซิร์ฟเวอร์รีสตาร์ท ประวัติจะสูญหาย สามารถลบรายการ einzelnen ได้ผ่านหน้านี้หรือผ่าน API `DELETE /v1/session/:id`

### 14.7 หน้าระบบและรายงาน (`system.html`)

**เส้นทาง:** `admin/pages/system.html`  
**บทบาท:** admin / editor / viewer (ดูได้ทุกบทบาท, จัดการคอนฟิกได้เฉพาะ admin)  
**API ที่ใช้:** `GET /api/admin/v1/system/health`, `GET /api/admin/v1/system/audit-logs`, `GET /api/admin/v1/system/config`, `PUT /api/admin/v1/system/config/:key`

หน้าสำหรับตรวจสอบสถานะระบบ ดูบันทึกการดำเนินการ (Audit Logs) และจัดการคอนฟิกส่วนกลาง

**ฟีเจอร์หลัก:**
- ตรวจสอบสถานะระบบ (Health) แสดงว่าเซิร์ฟเวอร์ทำงานปกติหรือไม่
- บันทึกการดำเนินการ (Audit Logs) แสดงในตาราง (เวลา, ผู้ใช้, การดำเนินการ, ประเภท, รหัสอ้างอิง)
- คอนฟิกส่วนกลาง (ระบบ) แสดงรายการ Key-Value คอนฟิกทั้งหมด
- ปุ่มเพิ่ม/แก้ไขคอนฟิก (เฉพาะบทบาท admin)

**ขั้นตอนการใช้งาน:**
1. เปิดหน้า `system.html` ระบบจะตรวจสอบสถานะเซิร์ฟเวอร์โดยอัตโนมัติ
2. ดูสถานะระบบในการ์ดสถิติด้านบน (สีเขียว = ปกติ, สีแดง = ผิดปกติ)
3. ดูบันทึกการดำเนินการในตาราง "บันทึกการดำเนินการ (Audit Logs)"
4. ดูคอนฟิกส่วนกลางในตาราง "คอนฟิกส่วนกลาง (ระบบ)"
5. เพิ่มหรือแก้ไขคอนฟิก: คลิก "เพิ่ม/แก้ไขคอนฟิก" กรอก Key, Value, คำอธิบาย แล้วคลิก "บันทึกคอนฟิก" (เฉพาะ admin)

## 15. คู่มือจัดการฐานความรู้ (Knowledge Base Management)

ฐานความรู้ของระบบ Chatbot ก.พ.ร. ประกอบด้วยสองส่วน:

1. **ฐานความหักหลัก (`knowledge/opdc-knowledge.json`)** — ข้อมูลหลักขององค์กร ก.พ.ร. (วิสัยทัศน์, ภารกิจ, ยุทธธรรม, คณะกรรมการ, บริการ ฯลฯ) จัดการโดยทีมพัฒผ่านไฟล์ JSON โดยตรง
2. **ชิ้นข้อมูลที่อัพโหลดเพิ่มเติม (`knowledge/uploaded-knowledge.json`)** — ชิ้นข้อมูลที่ผู้ดูแลระบบอัพโหลดผ่านหน้าเว็บหรือ API เพื่อเสริมฐานความรู้ (ไฟล์นี้ไม่ถูกเก็บใน Git เนื่องจากมีข้อมูลที่สร้างขณะรันระบบ)

---

### 15.1 โครงสร้างไฟล์ `knowledge/opdc-knowledge.json`

ไฟล์นี้เก็บข้อมูลหลักขององค์กร ก.พ.ร. ในรูปแบบ JSON มีส่วนหลักดังนี้:

| ส่วน | รายละเอียด |
|------|-------------|
| `meta` | ข้อมูลเกี่ยวกับฐานความรู้ (ชื่อ, คำอธิบาย, แหล่งที่มา, วันที่อัปเดตล่าสุด) |
| `organization` | ข้อมูลองค์กร (ชื่อ TH/EN, ย่อ, ที่อยู่, โทรศัพท์, แฟกซ์, อีเมล, Facebook, YouTube) |
| `vision` | วิสัยทัศน์ขององค์กร (ภาษาไทย/อังกฤษ) |
| `mission` | ภารกิจขององค์กร (ภาษาไทย/อังกฤษ) |
| `strategic_issues` | ประเด็นยุทธศาสตร์ 5 ประการ (แต่ละรายการมี id, ชื่อ TH, คำอธิบาย TH) |
| `committees` | คณะกรรมการต่าง ๆ (ก.พ.ร., ค.ต.ป., กพม., อนุกรรมการ) |
| `knowledge_center` | ศูนย์ความรู้และหมวดหมู่เอกสาร |
| `quick_links` | ลิงก์ด่วนไปยังระบบต่าง ๆ ของภาครัฐ |
| `services` | บริการที่องค์กรให้ (ชื่อ TH, คำอธิบาย TH) |
| `events` | กิจกรรมที่กำลังจะมาถึง (ชื่อ TH, วันที่ TH, คำอธิบาย TH) |
| `channels` | ช่องทางการติดต่อและร้องเรียน |

**ตัวอย่างโครงสร้าง (ย่อ):**

```json
    "source": "https://www.opdc.go.th/",
    "last_updated": "2026-10-09"
  },
  "organization": {
    "name_th": "สำนักงานคณะกรรมการพัฒนาระบบราชการ",
    "name_en": "Office of the Public Sector Development Commission",
    "abbr_th": "ก.พ.ร.",
    "abbr_en": "OPDC",
    "address": "59/1 ถนนพิษณุโลก แขวงดุสิต เขตดุสิต กรุงเทพฯ 10300",
    "phone": "02 356 9999",
    "email": "contact@opdc.go.th"
  },
  "vision": {
    "text_th": "พัฒนาระบบราชการตามหลักธรรมาภิบาลให้เกิดผลอย่างเป็นรูปธรรม"
  },
  "mission": {
    "text_th": "..."
  },
  "strategic_issues": [
    { "id": "1", "title_th": "...", "desc_th": "..." }
  ],
  ...

```

**การแก้ไข:** แก้ไขไฟล์ `knowledge/opdc-knowledge.json` โดยตรงด้วยเครื่องมือแก้ไขข้อความใด ๆ แล้วบันทึก ระบบจะอ่านไฟล์ใหม่เมื่อเริ่มเซิร์ฟเวอร์หรือเมื่อโหลดฐานความรู้ใหม่

### 15.2 โครงสร้างชิ้นข้อมูล (Chunk) ที่อัพโหลดเพิ่มเติม

ชิ้นข้อมูลที่อัพโหลดผ่านหน้าเว็บ (`knowledge.html`) หรือ API จะถูกเก็บใน `knowledge/uploaded-knowledge.json` โดยแต่ละชิ้นมีโครงสร้างดังนี้:

| ฟิลด์ | ชนิด | รายละเอียด |
|-------|------|-------------|
| `id` | string | รหัสชิ้นข้อมูล รูปแบบ `upload_<timestamp>_<index>` เช่น `upload_1793157183886_0` |
| `category` | string | หมวดหมู่ โดยปกติคือ `"uploaded"` |
| `keywords` | string[] | คำสำคัญที่แยกจากเนื้อหา (ใช้สำหรับการค้นหาแบบคีย์เวิร์ด) |
| `title` | string | ชื่อหรือที่มา (เช่นชื่อไฟล์ต้นฉบับ) |
| `sourceUrl` | string\|null | URL ของแหล่งอ้างอิง (ถ้ามี) |
| `publisher` | string | ผู้เผยแพร่ (สำหรับไฟล์อัพโหลดคือ `"user_uploaded"`) |
| `documentStatus` | string | สถานะเอกสาร (เช่น `"uploaded"`, `"published"`) |
| `content` | string | เนื้อหาข้อความเต็มของชิ้นข้อมูล |
| `text` | string | เนื้อหาข้อความ (ซ้ำกับ content) |
| `uploadedAt` | string | วันที่และเวลาที่อัพโหลด (รูปแบบ ISO 8601) |
| `originalFile` | string | ชื่อไฟล์ต้นฉบับที่อัพโหลด |

**ตัวอย่างชิ้นข้อมูล:**

```json
{
  "id": "upload_1793157183886_0",
  "category": "uploaded",
  "keywords": ["นโยบาย", "การลา", "งาน", "กพร", "ลาป่วย", "ลาพักร้อน", "ลากิจ"],
  "title": "นโยบายการลางาน.pdf",
  "sourceUrl": null,
  "publisher": "user_uploaded",
  "documentStatus": "uploaded",
  "content": "นโยบายการลางานของ ก.พ.ร. ให้ลาป่วยได้สูงสุด 30 วันต่อปี และลาพักร้อนได้ 10 วันต่อปี พนักงานสามารถลากิจได้ไม่เกิน 5 วันต่อปี",
  "text": "นโยบายการลางานของ ก.พ.ร. ให้ลาป่วยได้สูงสุด 30 วันต่อปี และลาพักร้อนได้ 10 วันต่อปี พนักงานสามารถลากิจได้ไม่เกิน 5 วันต่อปี",
  "uploadedAt": "2026-10-28T03:13:03.886Z",
  "originalFile": "นโยบายการลางาน.pdf"
}
```

---

### 15.3 การจัดการชิ้นข้อมูลผ่านหน้าเว็บ (`knowledge.html`)

เปิดหน้า `admin/pages/knowledge.html` (ต้องล็อกอินก่อน บทบาท admin หรือ editor)

**เพิ่มชิ้นข้อมูลใหม่:**
1. กรอกชื่อหรือที่มา (เช่น `นโยบายการลางาน.pdf`) ในช่อง "ชื่อหรือที่มา"
2. กรอกเนื้อหาข้อความในช่อง "เนื้อหาข้อความ"
3. คลิกปุ่ม "เพิ่มชิ้นข้อมูล"
4. ระบบจะแยกข้อความเป็นชิ้นย่อยโดยอัตโนมัติ (แบ่งตามย่อหน้า ถ้าย่อหน้ายาวจะแยกตามประโยค ขนาดสูงสุด 500 ตัวอักษรต่อชิ้น)
5. ชิ้นข้อมูลใหม่จะปรากฏในตารางรายการด้านล่าง

**ดูรายการชิ้นข้อมูลทั้งหมด:**
- ตารางแสดง รหัส, ชื่อ/ที่มา, ประเภทสถานะ, วันที่อัพโหลด, การดำเนินการ
- แสดงจำนวนชิ้นข้อมูลทั้งหมดที่ด้านบนตาราง

**ลบชิ้นข้อมูล:**
1. คลิกปุ่ม "ลบ" ในแถวของชิ้นข้อมูลที่ต้องการลบ
2. ยืนยันการลบในกล่องโต้ตอบ
3. ชิ้นข้อมูลจะถูกลบออกจากรายการและจากไฟล์ `knowledge/uploaded-knowledge.json`

---

### 15.4 การจัดการชิ้นข้อมูลผ่าน API

ใช้ endpoint ภายใต้ `/api/admin/v1/knowledge/*` (ต้องล็อกอิน และต้องมี CSRF token สำหรับคำขอที่เปลี่ยนสถานะ)

| เมธอด | เส้นทาง | คำอธิบาย | บทบาท |
|-------|---------|-----------|-------|
| GET | `/api/admin/v1/knowledge/chunks` | ดูรายการชิ้นข้อมูลทั้งหมด | admin, editor, viewer |
| POST | `/api/admin/v1/knowledge/chunks` | เพิ่มชิ้นข้อมูลใหม่ (ต้องมี CSRF) | admin, editor |
| DELETE | `/api/admin/v1/knowledge/chunks/:id` | ลบชิ้นข้อมูลตามรหัส (ต้องมี CSRF) | admin, editor |

**ตัวอย่างการเพิ่มชิ้นข้อมูลผ่าน cURL:**

```bash
curl -X POST http://localhost:8001/api/admin/v1/knowledge/chunks \
  -H "Content-Type: application/json" \
  -H "X-CSRF-Token: <csrfToken>" \
  -b "session_id=<sessionCookie>" \
  -d '{
    "title": "นโยบายการลางาน.pdf",
    "content": "นโยบายการลางานของ ก.พ.ร. ให้ลาป่วยได้สูงสุด 30 วันต่อปี และลาพักร้อนได้ 10 วันต่อปี พนักงานสามารถลากิจได้ไม่เกิน 5 วันต่อปี"
  }'
```

**ตัวอย่างการลบชิ้นข้อมูลผ่าน cURL:**

```bash
curl -X DELETE http://localhost:8001/api/admin/v1/knowledge/chunks/upload_1793157183886_0 \
  -H "X-CSRF-Token: <csrfToken>" \
  -b "session_id=<sessionCookie>"
```

### 15.5 การสำรองและกู้คืนฐานความรู้

**สำรองไฟล์ฐานความรู้หลัก:**


**สำรองชิ้นข้อมูลที่อัพโหลดเพิ่มเติม:**

```bash
# สำเนาไฟล์ชิ้นข้อมูลที่อัพโหลด (ไฟล์นี้ไม่ถูกเก็บใน Git)
cp knowledge/uploaded-knowledge.json knowledge/uploaded-knowledge.json.backup.$(date +%Y%m%d%H%M%S)
```

**กู้คืน:** หยุดเซิร์ฟเวอร์ แล้วคัดลอกไฟล์สำรองกลับทับไฟล์ต้นฉบับ แล้วเริ่มเซิร์ฟเวอร์ใหม่

### 15.6 หมายเหตุสำคัญ

1. **ไฟล์ `knowledge/uploaded-knowledge.json` ไม่ถูกเก็บใน Git** — ถูกระบุใน `.gitignore` เนื่องจากเป็นข้อมูลที่สร้างขณะรันระบบ ควรสำรองแยกต่างหาก
2. **ชิ้นข้อมูลที่อัพโหลดจะถูกใช้โดย Chatbot ทันที** — สำหรับการค้นหาคำตอบแบบคีย์เวิร์ด (rule-based matching)
3. **การแยกชิ้นข้อมูล** — เมื่ออัพโหลดข้อความยาว ระบบจะแยกเป็นชิ้นย่อยโดยอัตโนมัติ (แบ่งตามย่อหน้า แล้วแบ่งตามประโยคถ้าย่อหน้ายาวเกิน 500 ตัวอักษร)
4. **รหัสชิ้นข้อมูล** — ใช้รูปแบบ `upload_<timestamp>_<index>` รับประกันว่าไม่ซ้ำกัน
5. **PDPA** — ชิ้นข้อมูลที่อัพโหลดไม่ควรมีข้อมูลส่วนบุคคลของผู้ใช้ หากพบให้ลบทิ้งทันทีผ่านหน้าเว็บหรือ API

## 16. คู่มือการติดตั้ง Production (Production Deployment Guide)

เอกสารนี้อธิบายขั้นตอนการติดตั้งและตั้งค่าระบบหลังบ้านแอดมินในสภาพแวดล้อม production รวมถึงตัวแปรสภาพแวดล้อมที่จำเป็น ข้อควรระวังด้านความปลอดภัย และขั้นตอนการติดตั้งทีละขั้นตอน

---

### 16.1 ตัวแปรสภาพแวดล้อมที่จำเป็น

สร้างไฟล์ `.env` ในโฟลเดอร์ `backend/` ก่อนรันเซิร์ฟเวอร์ใน production:

```env
# พอร์ตที่เซิร์ฟเวอร์จะรัน (ค่าเริ่มต้น: 8001)
PORT=8001

# สภาพแวดล้อมการทำงาน (development หรือ production)
NODE_ENV=production

# คีย์ลับสำหรับเซสชันแอดมิน — **จำเป็นต้องตั้งใน production**
# ใช้สตริงสุ่มอย่างน้อย 32 ตัวอักษร เปลี่ยนทุกครั้งที่ติดตั้งใหม่
ADMIN_SESSION_SECRET=<สตริงสุ่มอย่างน้อย 32 ตัวอักษร เช่น เปลี่ยนทุกครั้งที่ติดตั้งใหม่>

# รหัสผ่านสำหรับอัพโหลดไฟล์เสริมฐานความรู้ (ค่าเริ่มต้น: opdc-admin-2026)
# แนะนำให้เปลี่ยนเป็นรหัสที่ปลอดภัยใน production
ADMIN_UPLOAD_KEY=เปลี่ยนเป็นรหัสผ่านของคุณ
```

**หมายเหตุสำคัญ:**
- `ADMIN_SESSION_SECRET` ต้องตั้งเสมอใน production มิฉะนั้นเซิร์ฟเวอร์จะไม่เริ่มทำงาน (หยุดด้วยข้อผิดพลาดร้ายแรง)
- ไฟล์ `.env` ไม่ถูกเก็บใน Git (ระบุใน `.gitignore`) ควรเก็บไว้บนเซิร์ฟเวอร์เท่านั้น
- ไม่ควร commit ค่าจริงของ `ADMIN_SESSION_SECRET` หรือ `ADMIN_UPLOAD_KEY` ลงในระบบควบคุมเวอร์ชัน

---

### 16.2 การสร้างบัญชีแอดมินคนแรก (First Admin Provisioning)

ก่อนใช้งานระบบหลังบ้าน ต้องสร้างบัญชีแอดมินคนแรกผ่านสคริปต์ provisioning:

```bash
cd backend
ADMIN_USERNAME=admin ADMIN_PASSWORD=ChangeMe123! ADMIN_ROLE=admin node scripts/create-admin.js
```

ข้อกำหนดรหัสผ่าน: อย่างน้อย 8 ตัวอักษร

หลังสร้างแล้ว รหัสผ่านจะถูกแฮชด้วย bcrypt ก่อนบันทึกลงฐานข้อมูล SQLite (`backend/database/admin.db`) ไม่มีการเก็บรหัสผ่านเป็นข้อความธรรมดา

หากบัญชีนี้มีอยู่แล้ว สคริปต์จะแจ้งว่า `"ผู้ใช้ 'admin' มีอยู่แล้วในระบบ"`

---

### 16.3 ขั้นตอนการติดตั้ง Production

```bash
# 1) โคลนหรืออัปโหลดโค้ดมายังเซิร์ฟเวอร์
cd /path/to/opdc-chatbot

# 2) เข้าโฟลเดอร์ backend และติดตั้ง dependencies
cd backend
npm install --production

# 3) สร้างไฟล์ .env ด้วยตัวแปรสภาพแวดล้อมที่จำเป็น
cat > .env << 'EOF'
PORT=8001
NODE_ENV=production
ADMIN_SESSION_SECRET=<สร้างสตริงสุ่มอย่างน้อย 32 ตัวอักษร>
ADMIN_UPLOAD_KEY=<รหัสผ่านสำหรับอัพโหลดไฟล์>
EOF
```

### 16.4 การรันเซิร์ฟเวอร์ใน Production (แนะนำให้ใช้ Process Manager)

แนะนำให้ใช้ **PM2** หรือระบบจัดการกระบวนการอื่นเพื่อให้เซิร์ฟเวอร์ทำงานต่อเนื่องและเริ่มต้นอัตโนมัติเมื่อเซิร์ฟเวอร์รีสตาร์ท:

```bash
# ติดตั้ง PM2 (หากยังไม่มี)
npm install -g pm2

# รันเซิร์ฟเวอร์ด้วย PM2
cd backend
pm2 start server.js --name "opdc-chatbot-admin"

# บันทึกรายการกระบวนการของ PM2
pm2 save

# ตั้งให้ PM2 เริ่มต้นอัตโนมัติเมื่อระบบบูต
pm2 startup
```

หรือใช้ระบบอื่น เช่น systemd, Docker, หรือระบบจัดการกระบวนการที่องค์กรใช้อยู่

### 16.5 ข้อควรระวังด้านความปลอดภัยใน Production

| รายการ | คำแนะนำ |
|--------|----------|
| `ADMIN_SESSION_SECRET` | ต้องตั้งเสมอ ใช้สตริงสุ่มอย่างน้อย 32 ตัวอักษร ไม่ควรเก็บใน Git |
| คุกกี้เซสชัน | ตั้งค่า httpOnly, sameSite=lax, secure (เฉพาะ production ที่ใช้ HTTPS) |
| Rate limiting | จำกัด 10 ครั้งล็อกอินผิดต่อ IP ภายใน 15 นาที ป้องกัน brute force |
| CSRF protection | ทุก endpoint ที่เปลี่ยนสถานะต้องส่ง header `X-CSRF-Token` |
| ไฟล์ที่อัพโหลด | `knowledge/uploaded-knowledge.json` ไม่ถูกเก็บใน Git ควรสำรองแยกต่างหาก |
| `cookies.txt` / `cookies_invalid.txt` | ไม่ควร commit ลง Git (มีโทเค็นเซสชันที่อาจละเอียดอ่อน) |
| ฐานข้อมูล SQLite | `backend/database/admin.db` ควรสำรองเป็นประจำ |
| HTTPS | ใน production ควรใช้ HTTPS เพื่อป้องกันการดักจับคุกกี้เซสชันระหว่างส่ง |

### 16.6 การสำรองและกู้คืนใน Production

**สำรองฐานข้อมูล SQLite:**

```bash
cp backend/database/admin.db backend/database/admin.db.backup.$(date +%Y%m%d%H%M%S)
```

**สำรองชิ้นข้อมูลความรู้ที่อัพโหลดเพิ่มเติม:**

```bash
cp knowledge/uploaded-knowledge.json knowledge/uploaded-knowledge.json.backup.$(date +%Y%m%d%H%M%S)
```

**กู้คืน:** หยุดเซิร์ฟเวอร์ คัดลอกไฟล์สำรองกลับทับไฟล์ต้นฉบับ แล้วเริ่มเซิร์ฟเวอร์ใหม่

### 16.7 ตรวจสอบว่าระบบทำงานปกติหรือไม่

หลังติดตั้งเสร็จ ให้ทดสอบดังนี้:

```bash
# 1) ตรวจสอบสถานะเซิร์ฟเวอร์
curl http://localhost:8001/health
# คาดหวัง: {"status":"ok","chunks_loaded":...,"uptime":...}

# 2) ทดสอบล็อกอิน (ควรได้ 200)
curl -X POST http://localhost:8001/api/admin/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"<รหัสผ่านที่ตั้งไว>"}'

# 3) ทดสอบดูรายการ Intent
curl http://localhost:8001/v1/intents

# 4) เข้าหน้าแอดมินในเบราว์เซอร์
# เปิด http://localhost:8001/admin/pages/login.html (หรือเส้นทางที่ตั้งค่าไว้)
```
